## What executes

`work/fast-decode.sqlite` is a 20-iteration decode of a 1920x1080, interleaved 4:4:4 JPEG produced by Fastvideo with DRI=10. Sequence per frame (same stream13):

1. Host uploads entropy byte stream.
2. `BytestreamMarkupMarkerAndFFKernel`, tail variant.
3. Two unsigned-integer global prefix scans, each BlockScan -> TopScan -> UpdateScan.
4. Four-byte D2H copy (count/result); `BytestreamUnstuffKernel`, tail variant.
5. Four-byte H2D error reset; `HuffmanDecodeKernel<SurfaceTrait<5>>`.
6. Four-byte D2H error readback.
7. `RleDecodeKernel<SurfaceTrait<5>>`.
8. For each of three color components: short prefix scan (Block/Top/Update), `DCSumKernel`, `DCRestoreKernel`.
9. `InverseDCTColorKernel<SurfaceTrait<5>>`.
10. 6,220,800-byte D2H pixel copy.

## Parallel byte unstuffing and marker indexing

The bulk markup kernel assigns eight source bytes (`uint2`) to each thread. It calculates byte masks for 0x00, 0xFF, and the second byte of RST0..RST7 or EOI. A 257-byte shared array conveys preceding-thread 0xFF state, with a direct predecessor global read at CUDA-block boundaries. It reduces counts over groups of16 threads (128 source bytes) using shuffle-down steps 8,4,2,1 and stores one count pair per group. Actual masks are structural byte tests; they do not parse Huffman codewords.

Two global scans convert counts into cumulative marker counts and cumulative retained-byte counts. The unstuff pass uses the same masks and 16-thread shuffle-up scans to give every thread disjoint output ranges. It converts FF00 into one FF, removes RST/EOI marker bytes, and records marker endpoint offsets in **bits**. The stored offset is `8 * unstuffed_output_byte_offset` (Unstuff extract lines241-245, further repetitions279,313,...). Thus boundaries generated by this GPU pass are byte aligned. Serial tail kernels handle fewer than128 remaining source bytes; their presence does not mean the whole stream is processed serially.

The resulting data are a marker-free, byte-unstuffed bit stream plus monotonically increasing segment endpoint offsets. There is no speculative arbitrary-bit-start decoder in this observed GPU pipeline.

## Huffman partitioning and state

Huffman extract lines27-52 computes:

```text
t = ((blockIdx.y * gridDim.x + blockIdx.x) * blockDim.x + threadIdx.x)
first_mcu = t * mcus_per_partition
if first_mcu >= mcu_count: return
start_bit = t == 0 ? 0 : endpoint_bits[t-1]
end_bit = endpoint_bits[t]
```

One CUDA thread serially reads Huffman codes for at most `mcus_per_partition` MCUs. Within each MCU it iterates three components, then the component's number of blocks packed in McuDesc. Table selectors are packed component-byte fields. It reads two32-bit input words lazily, uses PRMT 0x0123 to byte-reverse words, and limits a lookahead to31 available bits. It does not use warp shuffles or shared memory in this kernel. The first coefficient is decoded with a DC canonical table; following symbols use an AC canonical table. AC parsing tracks `k += run + 1`, terminates at EOB (`symbol==0`) or k>=64. It emits raw tokens rather than expanding zeros or accumulating DC predictors here.

The complete11-argument ABI, anchored by PTX loads and sibling CUPTI actual values:

|3|u64 pointer|partition endpoint bit offsets|device pointer|

McuDesc+0/+4 are not read by this Huffman specialization; their likely sampling-factor interpretation requires other-kernel evidence. The3components have blockcounts1,1,1 and bases0,1,2. The ABI pointer values are ephemeral device addresses, not file offsets.

For each canonical table, the code selects code-length index with a four-step binary decision tree (test9-bit prefix, then5/13, then3/7/11/15, then2/4/.../16). This is bounded log2(16) length selection, not a complete2^16-entry decode LUT. Runtime table upload is4480B, consistent with4*1120B tables. Proven accesses:

| Per-table relative byte offset | Access/role reconstructed from use |
|---:|---|
|+16|u8 Huffman symbol array, selected by canonical symbol index|
|+1040|u8 `valptr[length_index]`|
|+1056|u16 `mincode[length_index]`|
|+1088|u16 upper-bound-exclusive check for selected length|

DC selector i uses state base `1120*i`; AC selector i uses `2240+1120*i`. This does not establish unused struct fields0..15 or272..1039. The upper-bound-exclusive role follows the `prefix >= table[1088+2*k]` invalid-code test, not a source-level field name.

Canonical symbol index is `prefix + valptr[k] - mincode[k]`; Huffman length is `k+1`; total consumed bits is `k+1+(symbol & 15)`. Magnitude bits remain unsigned in the token. If decoding fails or a symbol needs more available bits, the thread atomically ORs4097 (`0x1001`) into the error word (line414). Only this error OR is atomic; no global work queue or decoder resynchronization loop appears.

## Intermediate token and coefficient layout

The token is exactly32bits:

```text
bits  0..7   symbol: high nibble=zero run, low nibble=amplitude category
bits  8..23  unsigned raw amplitude bits (before JPEG extend)
bits 24..31  total consumed bits = Huffman length + category
```

Proof: Huffman extract226 inserts raw magnitude into bits8..23; PRMT0x0654 at230 places symbol, magnitude low/high, consumed count in successive bytes; line238 writes32bits. RLE extract74 extracts16bits at offset8 and uses the token's low4bits as category. No sign extension until RLE.

Let N be padded MCU pitch (`Huffman param9`, `RLE param4`), m the MCU index, b the component-local block index plus McuDesc's component-block base, and j the token ordinal. Token index in32-bit units is:

```text
T[(b*64 + j)*N + m]
```

Adjacent decoding threads therefore write the same token ordinal for adjacent partitions into strided positions separated by the partition MCU count, whereas adjacent RLE threads work on consecutive MCUs and coalesce accesses to each token plane. Token slots are fixed-capacity64 per block, with EOB avoiding consumption of later undefined slots. This is not a compact variable-size global token buffer; 'compact tokens' describes each token's four bytes, not total allocation.

RLE assigns one thread to each MCU (254*128 launch covers32400). For each block, it expands the token run counts across all64 coefficient positions, emitting zeros as well as nonzeros. It writes signed16-bit coefficient planes:

```text
C[(destination_component_block_base*64 + coefficient_ordinal)*N + m]
```

There is no zigzag-to-natural permutation in RLE's address calculation: coefficient_ordinal is stream zigzag ordinal; any permutation required by IDCT is downstream. JPEG signed amplitude conversion is:

```text
s = symbol & 15
v = raw & ((1<<s)-1)
if v < (1<<(s-1)): v += 1 - (1<<s)
```

For s=0 result is0 (the PTX computes threshold as `(1<<s)>>1`, avoiding an invalid negative shift). High nibble supplies run count. EOB produces a target coefficient ordinal64 so all remaining positions become zero. Unrolled implementation writes four consecutive coefficient planes per loop. RLE stores each block's DC **difference**, not its predictor sum.

## DC dependency removed through scans

Three short global scans per frame correspond to three components, irrespective of the number of restart intervals. For444 there is one block per component perMCU. The mathematically equivalent operation is:

```text
P[m] = inclusive_prefix_sum(dc_delta[m])
segment_base[t] = t == 0 ? 0 : P[t*partition_mcus-1]
DC[m] = P[m] - segment_base[m/partition_mcus]
```

The implementation separates DCSum (extract33,59..103,116) and DCRestore (extract118 division and141..191 subtract/store). DCSum computes one baseline per partition. For components with H blocks/MCU, it sums all H per-block prefix planes at the previous MCU. DCRestore reconstructs in-MCU block order by starting from that combined preceding-MCU sum, adding each block's DC delta, and subtracting the partition baseline. This makes partition-local predictor restoration parallel across MCUs while retaining JPEG component predictor semantics.

## The no-restart case is materially different

The separate runtime `work/fast-decode-no-rst.sqlite` decodes a GPUJPEG-generated444 JPEG whose DRI segment explicitly contains0, no RSTs and no external segment index. Header inventory is reproducible with `markers.py`. It still invokes the same GPU Huffman/RLE/DC pipeline, so GPUJPEG's CPU entropy fallback is **not** the only workable approach.

The Huffman grid changes from13x256 (DRI10) to8x256. The sibling runtime-capture investigation captured actual launch argument8=16 (partition MCU count), argument7=32400 (actual MCUs), argument9=32416 (padded MCU pitch), and the16-byte McuDesc. Thus there are2025partitions, covered by2048threads. RST10 has3240partitions, covered by3328threads.

More importantly, each no-RST iteration uploads694474B of entropy payload even though the entire original JPEG is686167B and entropy starts at664. Conversely the DRI10 case uploads exactly697456B =698189(file size)-733(entropy start). The runtime-capture sibling captured the uploaded bytes and proved that they contain2024RST markers plusEOI and form validDRI16 entropy. Its independent parser (`work/runtime-capture/coeff_compare.py`) reconstructed all97200blocks*64 quantized coefficients from both the originalDRI0 source and the transformedDRI16 upload: **every coefficient is identical**, reconstructed coefficient SHA256 `970ef1ab0e07422c1688ba6df547f856cc1a3aa3e5bbc47b41dcf7961a1b0b01`. This establishes a **host-side lossless entropy transcode before upload**: insert restart partitions, re-encode DC at each newly reset predictor boundary, pad/byte-stuff, then use the normal GPU restart decoder. It is not pure-GPU no-RST Huffman discovery, and no host-produced offset array upload is needed. RST10 uploaded entropy is exactly the original entropy slice, confirming bypass of transcode for already partitioned input. Preserve the sibling's complete `coefficient-comparison.json`, `payload-analysis.json` and `capture.tsv` in the evidence deliverable.

Mean Huffman time grows from455.67us(DRI10) to715.43us(no-RST prepared partitioning); RLE remains about133-136us. This is not a fair standalone codec-performance comparison because JPEGs differ in producer/entropy data and host preparation costs are outside these kernel durations. No-RST host inter-frame gap is visibly larger in trace and must be included in an end-to-end comparison.

## GPUJPEG transfer relevance

GPUJPEG currently assigns a thread per restart segment and combines Huffman parsing, zero-run position handling, coefficient scatter, and DC predictor accumulation. A transfer of this observed architecture would separate: (1) coalesced byte unstuff/segment indexing, (2) canonical symbol parsing into plane-major tokens, (3) RLE expansion across MCU threads, (4) DC prefix restoration, (5) IDCT. This can reduce work in the dependency-heavy Huffman loop and coalesce coefficient writes, at the cost of substantial intermediate buffers and extra launches. It is not yet established that the split wins for GPUJPEG's current layouts/restart policy. The CPU no-RST transformation is a separate necessary part of Fastvideo's complete strategy, not obtained merely by adding a CUDA kernel.
